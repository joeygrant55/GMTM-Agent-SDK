# GMTM → SPARQ authentication implementation contract

September 10, 2026. **Specification only; no bridge, provider operation, account creation or deployment performed.** Builds on the [source-pinned GMTM handoff map](gmtm-auth-handoff-map-2026-09-10.md). Codex checkout at review: `codex/athlete-home-first-value`, `2e2539c` (`joeygrant55/GMTM-Agent-SDK`). GMTM deployment provenance remains the owner-confirmation item in that map; this task did not re-query those deployments.

## Decision and first deliverable

Keep Clerk as the SPARQ session layer. After GMTM verifies an adult's **self-owned** session, exchange a short-lived, browser-bound GMTM code server-to-server, resolve the exact existing athlete/Clerk link, and use a Clerk sign-in ticket only when that same Clerk identity is not already active. Bind the resulting Clerk session to continuing GMTM authority before admitting personal SPARQ requests. This preserves the current athlete data adapters, authored work and Clerk UI.

The first coding milestone is **existing-link authorization planning, entirely offline**, limited to `backend/gmtm_auth.py` and `backend/tests/test_gmtm_auth.py`. Validate a self-owned adult assertion and the exact existing link, then decide whether to reuse a matching Clerk session, require a ticket, report an account conflict or deny access. Inject clock and link reader; reuse forward/reverse ownership rules and link revision. Its completion evidence is the decision matrix and fixtures for expiry, ambiguous links, switched/delegated authority and conflicting accounts. No connections, provider operations, transaction store or schema are needed.

The following milestones separately implement ticket/session activation, then the browser entry and revocation journey with synthetic GMTM/Clerk adapters. Only that later integration milestone must reach the actual Home. New-user provisioning, identifier verification and native entry remain separate. Do not edit the legacy uploader or replace the current authentication mode to finish the initial planner. Activation and real identity/provider writes come only after the deployment-owner checks below and an exact reviewed live test. Existing read-only preview/save budgets do not authorize user creation, ticket issuance or link writes.

Current architecture matters: authentication dependencies return a Clerk ID string, so session/grant validation belongs at that boundary without forcing every resource handler to accept a new principal object. Candidate middleware denies the proposed same-origin auth POSTs until exact coordinated policy changes are tested. Agent MySQL and GMTM Redis have different owners; establish transaction/binding storage ownership before implementing either store.

## Identity admission and link outcomes

The GMTM assertion must contain a version, exact issuer/audience, random grant ID, issued/expiry times, source-session reference, `actor_user_id`, `athlete_user_id`, `session_kind: self`, authentication provenance/time, adult classification and structured return context. The source reference is opaque outside GMTM; the long-lived GMTM bearer never crosses into SPARQ. Only GMTM may assert these fields after checking the current Redis `sessions` record and necessary current account facts. Reject unverified-user records, inactive accounts, missing/future/malformed identity evidence and `actor != athlete`.

The old session shape does not establish actor provenance. An absent `parent_id`, an athlete role, an adult combine, a matching email, or a frontend “not impersonating” flag is insufficient. In particular, an old switched-child session can outlive detach. **Unmarked legacy sessions require owner-reviewed migration evidence or a one-time re-authentication in GMTM that creates a self-provenance record.** Subsequent routine entries reuse that valid authority. Adult admission uses the reviewed current-age rule/source, not the competition's age-at-December-2027 cutoff. Unknown age is ineligible for this initial slice.

| Current state after verified GMTM exchange | Exact behavior |
| --- | --- |
| One current forward/reverse link to Clerk A; browser signed out | Read Clerk A by its exact ID, require usable account and no contradictory external identity; mint a short ticket for A. Preserve link ID and every workspace row. |
| Same link; browser already Clerk A | Verify the current Clerk session and source grant, then bind/reuse that exact session. No ticket, duplicate session, profile creation or authored-work write needed. |
| GMTM athlete linked to A; browser active as Clerk B | Stop before ticket/session/link changes. Explain the account mismatch without disclosing another person's identifiers. Offer an explicit account-switch/recovery path that protects the current draft; no silent `setActive`, sign-out or reassignment. |
| No athlete link; browser already Clerk A | Do not silently attach. A dedicated confirm-link step requires both the verified GMTM assertion and fresh valid Clerk A session, shows the self-owned account being connected, and applies the same reverse-ownership conflict policy as claims. |
| No link; no active Clerk identity | Provision only after the new-user admission/identifier decision is verified. Use namespaced immutable `externalId = gmtm:<environment>:<athlete-id>`, an idempotent provisioning record, and only contact data whose verification GMTM can substantiate. A pre-existing email without the exact external identity enters recovery, not auto-linking. |
| Null/malformed Clerk value, multiple forward matches, reverse mismatch, retired/recreated link or unexpected external identity | Fail closed with a recoverable conflict; never repair an ambiguous legacy row during sign-in. |

Agent mapping insertion must cooperate with [claims' existing named Clerk lock and transactional no-op-on-conflict insert](../../backend/claims_api.py#L251). The current Clerk index is not unique: reuse the same `sparq.claim.<hash>` lock convention, then lock/read both directions and retain the generated `athlete_profiles.id`. Preserve [_owner / link revision](../../backend/athlete_workspace.py#L152). No in-place mapping swaps, resets, broad updates, claim redemption side effects or calls that silently bootstrap a different profile model.

Clerk and MySQL cannot commit atomically. Use a durable, uniquely keyed provisioning operation: reserve → resolve/create Clerk identity → confirm exact mapping → issue ticket → bind active session. Concurrent requests for the same external identity converge or conflict. If a provider response is uncertain, reconcile by the exact external ID/operation before retrying; never blindly create another user/ticket. A newly created but unlinked Clerk user is recorded as partial progress and receives no access. Do not delete accounts as automatic compensation. Prepare this ledger/schema offline; live creation/migration is a separate concrete action.

## Browser and server exchange

These are proposed exact interfaces, not existing routes. The security decisions follow [OAuth Security BCP](https://www.rfc-editor.org/rfc/rfc9700.html): bind the response to its initiating browser, enforce PKCE S256 and exact callbacks, prevent code replay, and keep authorization material out of third-party content and logs.

1. **Start on SPARQ, even when the CTA is on GMTM.** `GET /auth/gmtm/start` serves a minimal initiation page; its same-origin CSRF-protected `POST /api/auth/gmtm/start` creates a five-minute transaction. Store random state and S256 verifier server-side, bind to a random `__Host-sparq-auth-tx` Secure/HttpOnly/SameSite=Lax cookie, the configured issuer/client/callback, and requested structured return IDs. No personal work loads on this page. A same-origin origin check is mandatory on POST; a top-level cross-site GET alone must not mint a Clerk credential or switch accounts.
2. Redirect to the fixed first-party GMTM authorization page with only state, S256 challenge, client ID and approved callback. GMTM reads its own cookie/server session; native entry must use the separately reviewed mobile launch binding below. Require an explicit athlete-initiated authorization when the incoming browser transaction cannot be proven to originate from the signed-in CTA. The GMTM page's issuance POST has its own CSRF/origin check. Never use `/sessions/ids` as introspection, generic `/verify`, or the old request-OTP exchange.
3. GMTM issues one random opaque **60-second** authorization code bound to the source session, actor/athlete, challenge, exact callback/audience and return context. Store its hash in a dedicated Redis namespace. `POST /v2/agent-handoff/exchange` is a confidential server-to-server operation: client authentication plus code and verifier are required. Validate all bindings and atomically consume with a fresh source-session/provenance check. A second successful consume is impossible across processes. Expiry, cancellation or uncertain consumption requires a new transaction, not replay of the old code.
4. `GET /auth/gmtm/callback?code=…&state=…` validates the transaction cookie/state, reserves the transaction once and exchanges server-to-server. Query secrets are scrubbed at app **and ingress** logs; respond no-store/no-referrer and redirect immediately to clean `/auth/gmtm/finish`. No analytics or third-party assets on the callback. Return URLs must be derived from allowlisted route kinds/positive IDs, never arbitrary incoming URLs. The clean completion page obtains the short Clerk ticket through a same-origin CSRF-protected POST only after link/conflict checks.
5. In memory, the Core 2 completion component calls `signIn.create({strategy:'ticket',ticket})`, handles incomplete status without opening Home, and calls `setActive` only for the expected subject after successful completion. No ticket in local/session storage, URLs, receipts, client logs or serialized error bodies. No automatic network retry after uncertain ticket consumption. An already matching session follows the no-ticket branch.
6. `POST /api/auth/gmtm/complete` verifies the real active Clerk JWT/session, exact subject, nonempty `sid`, no `act`, active provider status and original transaction. Backend rechecks current GMTM grant and strict Agent link/revision, then creates a unique binding of Clerk `sid` → subject + link ID + GMTM grant. A caller-supplied session ID is not proof. No personal API is authorized while completion is pending.
7. Home uses its existing JWT transport. The bridge-enabled backend's personal-route dependency resolves the session binding and revalidates GMTM authority **before** source reads, workspace writes or provider calls. Require signature/issuer/exact authorized party, valid subject/session/times and absent impersonation; retain existing per-resource ownership and optimistic workspace version checks. A valid standalone Clerk token without an active bridge binding cannot bypass this mode. Explicit bridge routes are the only additions to candidate route/package/config guards.

Store transaction, provision and session-binding records in a reviewed Agent-owned store behind injected adapters; do not use process-local state as a distributed one-use guarantee. Store only hashed random handles where lookup permits; expiry/retention and exact DDL are separate reviewed artifacts. Credentials remain in server environments, with separate pinned audience/client authentication for GMTM↔SPARQ and the SPARQ Next↔backend auth endpoints. Never trust a public `X-User-Id` or unsigned internal header. Existing personal API calls remain direct and Clerk-authenticated; no general-purpose API proxy is needed.

For the first slice, one active GMTM grant is bound to a Clerk `sid`; repeat matching entry reuses it after validation, and conflicting authority does not overwrite it. Return context is a separate, integrity-protected, subject-bound navigation receipt, not an authentication credential or replacement for grant validation. Keep it per entry/tab so opening another combine does not silently change an older tab's destination. Home refresh resolves it under the current session; invalid context falls back to GMTM home. The return remains a labeled new-tab link to protect unsaved drafts until deliberate same-tab save/leave UX is implemented.

## Revocation, account changes and mobile scope

For the first pilot, use **no positive cache** for the dedicated GMTM active-grant check on personal requests. The endpoint only reads current session/grant existence, expiry and self-provenance/account state; it does not refresh the source TTL or update last sign-in. Apply bounded timeouts and redacted errors. An unavailable validator returns temporary-unavailable, preserves the same-owner editor buffer and admits no data/mutation. Explicit revoked/expired/changed-identity results invalidate scope, abort pending requests and prevent cross-account display. Already-admitted in-flight operations have the ordinary request-boundary race; test revocation before the final write authorization check and document that limit instead of promising instantaneous global cancellation.

GMTM's actual web and mobile sign-out handlers must invoke server source-session/grant revocation, not only clear local cookies/storage. SPARQ sign-out first revokes its bridge grant/binding through an authenticated CSRF-protected endpoint, then ends that Clerk session; global GMTM sign-out revokes all bindings derived from that **source session**, not unrelated devices. Record/retry failed provider revocation server-side while the application binding is already denied. Pending ticket cancellation uses `revokeSignInToken`; a consumed ticket requires session revocation. Do not extend grant validity because a Clerk JWT refreshed. External Clerk revocation follows provider token semantics unless the application has also revoked the binding; do not claim signature verification alone provides immediate provider revocation.

Switching GMTM to a different represented athlete invalidates the old bridge context; old SPARQ tabs must not repaint as the new athlete or move drafts. The initial release excludes parent/child switching. A future delegated principal must preserve operator, represented athlete, live guardian relation and their respective session provenance; Clerk impersonation alone cannot authorize it.

First acceptance is **GMTM web → SPARQ web**. Mobile should reuse the same exchange but must first bind the browser's SPARQ transaction to the authenticated native request (verified universal/app link rendezvous or a reviewed equivalent). Do not place a mobile session token in a browser URL, assume an external browser shares mobile cookies, or trust `@parentData` as authority. iOS/Android linking and resumed-account checks require their own owner-confirmed test. The existing source-pinned mobile navigation targets can carry validated event/task return IDs once that binding passes.

## Completion gates and owner decisions

The later complete browser integration is done when fixtures exercise real components/handlers across: existing-link signed-out ticket flow; existing matching session without ticket; first-user provisioning/reconciliation; signed-in conflict; both mapping directions and row revision; duplicate/concurrent consume and provision; missing/wrong cookie/state/verifier/issuer/audience/callback; source expiry/revoke/timeout; incomplete/failed/uncertain Clerk sign-in; foreign or impersonated `sid`; direct API bypass; sign-out/switch; and preserved goal/draft/context after reload. Assert exact permitted calls/writes and absence of credentials in URLs/logs/storage. Run one supervised heavy job at a time and retain source digests/cleanup receipts. Synthetic provider success does not establish configured Clerk acceptance.

Before enabling an actual pilot, deployment owners must verify:

1. Serving API/web commits and real signed-in CTA/logout paths; Redis topology/atomic operation and fresh self-session provenance. Decide which legacy sessions require one-time GMTM re-authentication, and which current-age evidence admits adults.
2. Exact SPARQ frontend/backend origins, Clerk instance/issuer and allowed parties; installed production SDKs; enabled required identifiers and legal/session/MFA tasks. Approve new-user verification provenance and collision/recovery policy. Existing exact-link entry can be verified independently of opening new-user enrollment.
3. Server-to-server client authentication, callback origins, transaction/provision/binding schema, TTL/retention and revocation behavior; effective ingress/error log redaction. No settings, schema or provider changes are authorized by this document.
4. One concrete isolated real-account test specifying target user, existing/new branch, ticket/session/account/link writes, maximum attempts and cleanup. The ordinary product approval to keep building is not an exhausted-budget reset. Prove actual Clerk issuance→activation→backend binding and GMTM logout denial before recruiting athletes.
